# Changelog

## [2.5.0] - 2026-10-24

### Added
- Auto Possess Player on Pawns placed in a level (opt-in, the only runtime change of this release): set it to Player 1 on the placed character and that player possesses it when it joins, instead of getting the GameMode's Default Pawn, as in Unreal. The GameMode finds the placed Pawns once as the level begins (into a reused list; nothing runs per frame and nothing is allocated afterwards), and the first time a player needs a Pawn `RestartPlayer` possesses the first free Pawn placed for it before spawning the Default Pawn. It is one-shot, as in Unreal: each player takes a placed Pawn at most once per level, so a later `RestartPlayer` (its Pawn died, it left the placed Pawn alive, or a second Pawn was placed for the same player) spawns the Default Pawn. A placed Pawn your code already possessed is left alone. The player wins over Auto Possess AI, as in Unreal: a placed Pawn with a player set does not get its AI controller as the level begins; it waits for its player. The default (-1, no player) keeps the previous behaviour, Auto Possess AI included. `Pawn.AutoPossessPlayer` reads and sets it from code.
- Editor support for it: a Possession section in the Pawn inspector (Auto Possess Player: No player, Player 1 to 8; "Controlled by: Player 1"; the AI section folds), notes for two placed Pawns that take the same player, an inactive one, a level without a GameMode, a player the level does not start with ("Waits for Player 2 to join", using the real Players at Start, so 0 means nobody joins until AddPlayer) and an Auto Possess AI that does nothing on a placed player's Pawn; the Selected GameMode panel and the Level overlay say 'Player 1 possesses the placed Pawn "X"' (or that it waits for Player 1 to join); the missing Player Start warning counts only the players that spawn the Default Pawn; with ObserverVM, "Bound by" binds the placed Pawn's widgets instead of saying "Pawn: none". `UEArchitectureActions.SetAutoPossessPlayer` and the verb `set-auto-possess-player`.
- Convert to framework class (a MonoBehaviour's gear > UE Architecture > Convert to GameMode…, Player Controller…, AI Controller…, Pawn…, HUD…, Player Start…, Loading Screen…, Game Instance…): a preview of the one line that changes (": MonoBehaviour" to ": GameMode<GameplayGameState, GameplayPlayerState>"), the GameState and PlayerState scripts it writes next to it (or existing classes picked with the arrow), methods that must become overrides calling the base class (OnDestroy on a Pawn or a controller), fields that would clash with the framework class's (refused: Unity cannot keep both), the framework fields that start with their defaults, and the scenes and prefabs that use it. "Rename class and file to GameplayGameMode" renames the class in its own file and the file through the Asset Database, so the GUID and every reference stay; after the compile a pending step (`uea.rename-objects`) renames the objects named after the old class in those prefabs and in the open levels (in batch mode, every level). Applying writes the plan the preview showed, is all or nothing and asks first; if the script changed on disk since the preview (byte for byte), nothing is written. Undo cannot take back a script edit, so "Copy original to clipboard" is offered. Only UTF-8 scripts are edited (with or without a byte order mark, which is kept); any other encoding is refused with "re-save it as UTF-8 first", so no accent is lost. The framework using goes after the last using every build compiles, never inside `#if UNITY_EDITOR`. Partial, nested, generic, repeated (#if) and commented declarations are refused with the reason; so is a rename when other scripts name the class (also qualified, as `MyGame.GameplayScene`, or inside an interpolated string) or when its own file has the old name after a dot, inside an interpolated string, or as an enum value, member, variable or parameter.
- Change Game State and Player State Classes… on a GameMode's gear menu: previews and rewrites the GameMode<A, B> line.
- Change Class… on the gear menu of GameMode, Player Controller, AI Controller, Pawn, HUD, Player Start, Loading Screen and Game Instance components: swaps the class in place on an object of a level or a prefab asset (only where the component was added, not one a prefab copy or a variant inherits), keeps the fields both classes have and lists the ones that are lost before asking. Unity's Undo cannot swap a class back, so the dialog says so; Change Class again restores the class, but the lost fields start empty.
- Find Usages in Scenes and Prefabs (Project window > right-click on a script > UE Architecture): the scenes and prefabs that use a class, directly or through a prefab, read from the files' dependencies with a progress bar that can be cancelled; the results are selected.
- New public actions `ConvertToFrameworkClass`, `FindUsages`, `ChangeComponentClass` and `ChangeGameModeStates` (each a dry run unless asked otherwise), and the verbs `convert-class`, `find-usages`, `change-class` and `change-gamemode-states`; the verbs that edit scripts or components only preview unless `apply=true`.
- Gameplay tag tools. A tag field's picker is a searchable tree (typing "burn" finds Status.Burning; a parent can be picked itself) with "None" first and "New tag…" last, which adds the tag to the project and puts it in the field. A value that is not a project tag shows "\"Status.Burnin\" is not a project tag" with [Add to project] and [Pick]. A tag container opens a checkbox tree (searchable; parents of a ticked tag show as mixed, since they match through it) with "New tag…", and its unknown entries offer [Add].
- Tag manager in Project Settings > UE Architecture > Gameplay Tags and in Window > UE Architecture > Gameplay Tags: the tags as a tree with search (the settings page's own search also finds tags by name), Add, Add sub-tag inline, Rename… ("Update 14 references in 6 assets; 2 levels listed, not changed": it renames the tag and the tags below it in Project Settings and in the GameplayTag and GameplayTagContainer fields of prefabs and every other native asset, text or binary: ScriptableObjects, Animator Controllers with their state machine behaviours, Timelines, signals, presets; names with letters outside ASCII are found too; values a prefab variant only inherits are left to its base; levels and scripts that use the name are listed, never changed; a level counts only its tag fields, not other text such as an object called like the tag, and the generated constants file is left out), Delete… (with how often it is used; the uses keep their value; the parent stays). Both search the project on the click, with a progress bar that can be cancelled, Find usages, and "Edit as a list" for the raw array.
- Generate C# constants: GameplayTags.g.cs with `Tags.Status.Burning` instead of `GameplayTag.Request("Status.Burning")`, in the root namespace of the file's assembly. A parent is a nested class whose own tag is `Tag` (`Tags.Status.Tag`); C# keywords get '@', a leading digit gets '_', and a name that would clash with its class gets '_'. The file goes in the scripts folder by default (Project Settings > UE Architecture > Editor > Tag Constants File); before writing, the folder's assembly is checked for a reference to UEArchitecture.Runtime, with "Add reference" (`fix-references=true`). An up-to-date file is left alone; a file at that path that the generator did not write is never overwritten. A name that needs no escaping always means its own tag, and tags whose C# names would clash ("1Up" and "_1Up", "X.Tag" and "X.Tag_") are refused with the pair to rename, so adding a tag never moves a constant to another tag.
- Project Settings > UE Architecture lists the subsystems as rows: the class, a Game or World chip, when it ticks ("Tick: LateUpdate, order 10, unscaled", from its `[Tick]`), [Open] and [Ping] its script, and [+ Game subsystem] [+ World subsystem], which open New Framework Class prefilled.
- Project Settings > UE Architecture lists the levels: the Build Settings scenes in their order (build index, disabled, missing file), then the other levels of the project, each with its GameMode and where it comes from (placed, World Settings override, project default, or none), World Settings and its Player Starts, and the fixes [Open], [Add to Build], [Set as first scene] and [Use project default] (clears the World Settings override). They are read from the saved level files, labelled approximate (objects inside nested prefabs are not seen), and cached per level file: a level is read again only when it, or a script or prefab it uses, changes, so the page scans nothing on repaint and its search compares names only. A World Settings placed as a prefab shows the prefab's own GameMode Override unless the level overrides it.
- New public actions in `UEArchitectureActions`: `AddTag`, `RenameTag`, `RemoveTag`, `FindTagUsages`, `GenerateTagConstants`, `SetFirstLevel`, `ListLevels` and `ListSubsystems` (with `AddSceneToBuild` and `ClearOverride` for the level fixes), and the command-line verbs `add-tag`, `rename-tag`, `remove-tag`, `find-tag-usages`, `generate-tag-constants`, `list-levels`, `list-subsystems`, `add-to-build` and `set-first-level`. A rename or a delete of a tag that an asset, a level or a script uses is a preview (exit code 2) until `apply=true`. Each refuses in Play mode, and a second run changes nothing.

### Changed
- The settings page answers a search for a tag, a subsystem or a level by name, and shows only the matching rows.
- `add-to-build` (and the Add to Build fixes) refuse in Play mode.

## [2.4.0] - 2026-10-24

### Added
- ObserverVM editor integration, a new editor assembly (UEArchitecture.ObserverVM.Editor) compiled only with ObserverVM 2.2 or newer (with ObserverVM 2.0 and 2.1 only the runtime integration compiles, as before). Through ObserverVM's public extension points:
  - "Bound by" in the widget inspector: what a widget will probably get and from whom (its HUD, a Framework Binder and which player, or nothing, in red, with Add Framework Binder), read without Play mode from the level's GameMode, the GameModes that use a HUD prefab, a placed GameMode's Pawn in the level, the project's GameInstance and the subsystem classes. `BindingPreview.Predict` follows `FrameworkViewModels.Resolve` step by step and a test keeps them equal. Static reading cannot see `ShouldCreate`, `SetViewModel` from code or `Bind.Child`, so the answers say "will probably bind"; a widget a parent widget holds keeps ObserverVM's own answer and never gets a binder. Inside a HUD the prediction follows GameMode.AddPlayer, which binds the HUD's widgets before it spawns the Pawn (a ViewModel the Pawn fits that is not a Pawn class gets what comes after the Pawn). A Framework Binder inside a HUD prefab is a warning (it binds its player before the HUD can, so every player's HUD would show that player), and so is a HUD placed in a level (only the HUD a GameMode spawns binds its widgets). Answers are cached until something changes, so inspectors do not read the project on every repaint.
  - A Framework Binder inspector: a Player 1/2... popup and what the widget will probably get (a player the GameMode does not start with gets no player objects: the binder only sees players that exist when the level begins); in Play mode the live object with Ping.
  - Bind Framework Widgets Below (GameObject > UE Architecture, Project right-click on a prefab): a checklist with the widgets a HUD or a parent widget binds unticked (also those of a prefab placed inside a HUD prefab); Apply adds the binders in one Undo step. On a prefab placed in a level the binder is an override on that copy, labelled so, or goes in the prefab with "Add to: The prefab" (`apply-to=prefab`); widgets with the same name are told apart. UE Architecture > Add Framework Binder on a widget's gear menu. Widgets ObserverVM's tools add for a framework object outside a HUD get a binder by themselves (Project Settings > UE Architecture > Editor > Add Framework Binders, on by default).
  - "Widgets in this HUD" in the HUD inspector: the GameModes that use the HUD (a popup picks the one to preview), each widget with what it will probably get or "nothing matches" with Open script, and "Add Widget for" with the GameState, PlayerState, Pawn, Player Controller, HUD class and subsystems that have an Observable, an ObservableList or a Command. An existing widget class is added inside the HUD at once and filled; otherwise a thin widget class is written and a pending step (`uea-ovm.hud-widget`) adds it inside the HUD prefab after the compile. "Create Widget for This" on framework scripts: inside a HUD, under a Canvas with a Framework Binder, or a prefab only; a class with nothing to show gets a message saying what to add. The Game Mode Kit's new HUD preset "HUD with Widgets for Game State and Player State" (`hud-preset=framework-widgets`) is offered when they have something to show, and says so when it adds nothing; it and the pending step save the HUD prefab file instead of opening Prefab Mode. A widget file that exists but declares another class is reported instead of waiting for a compile that never brings it.
  - A "Framework (UE Architecture)" group in ObserverVM's ViewModel pickers (GameState and PlayerState classes, subsystems).
  - Validation rules for ObserverVM's Validation window and its Play and build checks (warnings, never blocking): framework widgets nothing binds, with Add Framework Binder; framework widgets of a level without a GameMode, with "Use <the project's only GameMode> here"; HUD widgets nothing matches; a Framework Binder inside a HUD; framework widgets of a HUD placed in a level. The Level overlay and `-uea validate` show "Bind 2 widgets" for the level's unbound framework widgets. Prefabs outside a HUD depend on where they are placed and are not reported.
  - Public actions in `FrameworkWidgetActions` (`PredictBinding`, `BinderCandidates`, `AddFrameworkBinders`, `AddFrameworkBinder`, `HudWidgets`, `DescribeHudWidgets`, `WidgetTypesForHud`, `AddHudWidget`, `CreateWidgetFor`) and the command-line verbs `predict-binding`, `add-framework-binders` (`dry-run=true` lists what it would do), `add-framework-binder`, `hud-widgets`, `add-hud-widget` and `create-widget-for`.
- Pawn inspector: "Controlled by" (the player, as a GameMode's Default Pawn or a placed GameMode's Pawn; AI; nobody yet, also for a copy of the Default Pawn placed in a level and for a placed Pawn whose Auto Possess AI is "Spawned"), an AI section (folded for a player's Pawn) with Auto Possess AI and the AI Controller class field, and with Unity's AI module a Navigation section: Add NavMeshAgent + Path Following, Block Time and Block Distance inline, "Off the NavMesh" with Snap, "No NavMesh in this level". The Pawn's gear menu has Make AI Pawn and Add Path Following; a NavMeshAgent's gear menu and the Project window (several Pawn prefabs at once) have Add Path Following.
- New public actions in `UEArchitectureActions`: `MakeAIPawn`, `MakeAIPawns`, `SetAutoPossess`, `AddPathFollowing` and `SnapToNavMesh`, and the command-line verbs `make-ai-pawn`, `set-auto-possess`, `add-path-following` and `snap-to-navmesh`. Each is one Undo step and a second run changes nothing.

### Changed
- "Auto Possess AI with a plain AIController" is a warning with a fix (Create AI Controller prefab, or Use your only AI Controller class); a Pawn with an AI Controller but Auto Possess AI Disabled gets a note with a fix.
- Editor extension points for other editor assemblies: command-line verbs, Game Mode Kit HUD presets, HUD inspector sections (one that throws is logged once and skipped until it is registered again), and pending steps queued by another step's handler (they were dropped before).

## [2.1.0] - 2026-10-20

### Added
- Navigation, like Unreal's AI MoveTo: `Controller.MoveTo`, `MoveToActor`, `StopMovement`, `PauseMove`, `ResumeMove`, `MoveStatus` and the `OnMoveCompleted` override. Every move ends with exactly one result (`MoveOutcome`: Success, Partial, Blocked, Invalid, Aborted, with a `MoveReason`), decided from the path's state instead of a distance threshold: stale and lost paths, partial paths, off-mesh links, crowds and stuck agents are handled.
- `PathFollowing` component (added to a Pawn with a NavMeshAgent the first time it moves; works on any NavMeshAgent), `MoveRequest` (callback with an owner and a static lambda, coroutine `Wait()`, `await`), `MoveResult`.
- `NavigationSystem` level subsystem: ticks the moves in progress after every LateUpdate, without allocating.
- Editor: Path Following inspector with the live move and gizmos; moves in progress in the Debugger.
- Sample: Patrol (guards patrolling with MoveTo, a chase with MoveToActor, click to move, a NavMesh built at runtime).
- Tests: 40 navigation PlayMode tests, including random interruptions of 50 agents, an agent that keeps moving without getting anywhere, and zero-GC checks.

### Changed
- `GameMode.RestartPlayer` stops the Pawn's move and warps its NavMeshAgent, which kept walking from where it was.
- `Controller` and `Pawn` are `partial` classes (navigation lives in its own files).

### Fixed
- Tests: NavMesh links are removed with `NavMesh.RemoveLink`, since `NavMeshLinkInstance.Remove()` is obsolete in Unity 6.3.

Navigation needs Unity's built-in AI module (`com.unity.modules.ai`, on by default); without it, that part is left out.

## [2.0.0] - 2026-10-20
Rewritten as Unreal's gameplay framework. The 1.x API is removed (tag `v1.2.0`); see "Migrating from 1.x" in the README.

### Added
- `GameInstance` that starts by itself before the first scene, from any scene, configured in Project Settings > UE Architecture.
- `GameInstanceSubsystem` and `WorldSubsystem` (created by themselves, dependency-ordered initialization, `ITickable`, `Get<T>` without allocating).
- `World`: level lifecycle (`BeganPlay`, `EndingPlay`), typed getters for the GameMode, GameState, players and Pawns.
- `GameMode` / `GameMode<TGameState, TPlayerState>`, `GameState`, `PlayerState`, `Controller`, `PlayerController`, `AIController`, `Pawn` (with Auto Possess AI), `HUD`, `PlayerStart`, `WorldSettings`; `World.SpawnPawn`, `World.AIControllers`, bots with a PlayerState.
- GameInstance and game subsystem hooks: `OnLevelBeganPlay`, `OnLevelEndingPlay`.
- Tick groups and order for tickable subsystems: `[Tick(TickGroup.LateUpdate, Order = -10, Unscaled = true)]`.
- `GameplayTag` and `GameplayTagContainer` (hierarchical, allocation-free queries, Inspector picker, project tag list).
- `SaveGame` and `SaveGames` (slots, versions, atomic writes, async variants).
- `Levels`: `Open` with loading screens, `Stream` / `Unstream`, `LevelLoad` usable as callback, coroutine or `await`; `SceneReference`.
- `Messages`: typed struct messages without allocation.
- `Timers`: like FTimerManager, without allocation.
- `ListView<T>`: framework lists that can be looped with `foreach` without allocating.
- Optional ObserverVM integration: HUD Widgets bound to the framework by type, `FrameworkBinder`.
- Editor: Project Settings page, GameMode and World Settings inspectors, SceneReference drawer, Debugger window, script templates, GameObject menu, link.xml for IL2CPP.
- Samples: Arena, Arena + ObserverVM.
- PlayMode and EditMode tests, including zero-GC tests.

### Removed
- `SceneRoot`, `GameEvents`, ScriptableObject `GameState` / `PlayerState`, the `PersistentLevel` flow, `IDataPersistent` / `IPersistent`, the `Persistant` and `Root` prefabs.
